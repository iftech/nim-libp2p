### contradicts-spec (proven violations: 1, 2, 3, 5; unsettled reading: 6, 7)

#### Finding 1 (F-f765f301) — XPR ads are signed in envelope domain libp2p-peer-record, not libp2p-routing-state — **confirmed**, medium severity, high confidence

The spec's `VERIFY_ADVERTISEMENT` says `assert(envelope.domain == "libp2p-routing-state")`. `ExtendedPeerRecord.payloadDomain` returns `"libp2p-peer-record"`, and the domain is part of the signed buffer. Every advertisement this node builds fails verification in the spec's domain, and every advertisement signed in the spec's domain is rejected here, on REGISTER and on GET_ADS alike.

This does not establish a fault between nim-libp2p nodes, which agree with each other. An existing test asserts that peer records and extended records decode interchangeably, so the shared domain is deliberate and the document may be the side to change.

- Locations: `libp2p/extended_peer_record.nim:62-63` (`payloadDomain`).
- Repro: `make test …_1` (expect: nonzero) → observed: exit 2, `Check failed: ExtendedPeerRecord.payloadDomain() == SpecEnvelopeDomain`, `Check failed: ad.envelope.verify(SpecEnvelopeDomain)`, `Check failed: Advertisement.decode(envelope.encode()).isOk()`; 4 tests run, 1 OK, 3 FAILED.
- Second pass: confirmed — read `extended_peer_record.nim:62-63` and the signature buffer in `signed_envelope.nim`, ran the test and saw the domain assertion fail.
- Fix: decide which side is authoritative. Either return `"libp2p-routing-state"` from `payloadDomain` (a signed-format change that needs a network-wide switch) or change the spec's pseudocode.

#### Finding 2 (F-fe66cfe4) — XPR ads use envelope payload type 0x0301, not /libp2p/extensible-peer-record/ — **confirmed**, medium severity, high confidence

The spec says `assert(envelope.payload_type == "/libp2p/extensible-peer-record/")`. `ExtendedPeerRecord.payloadType` returns the two bytes `0x03 0x01`, the type of an ordinary libp2p peer record. Advertisements built here carry the wrong type, advertisements carrying the spec's type are rejected with `EnvelopeWrongType`, and a plain signed peer record passes the type check the spec uses to tell an advertisement apart.

The last effect is confined to the type assert: a plain peer record lists no services, so the later service check still drops it.

- Locations: `libp2p/extended_peer_record.nim:65-66` (`payloadType`).
- Repro: `make test …_2` (expect: nonzero) → observed: exit 2, `Check failed: ExtendedPeerRecord.payloadType() == SpecPayloadType.toBytes()` and three further failed checks; 5 tests run, 1 OK, 4 FAILED.
- Second pass: confirmed — read `extended_peer_record.nim:65-66` and `signed_envelope.nim:100-143`, ran the test and saw the payload type assertion fail.
- Fix: decide which side is authoritative. Either return the bytes of `/libp2p/extensible-peer-record/` (and drop the interchangeable-decoding test), coordinated network-wide, or change the spec's pseudocode.

#### Finding 3 (F-6e44602b) — 4096-byte reply read limit rejects GET_ADS responses carrying F_return valid ads — **confirmed**, medium severity, high confidence

The spec's GET_ADS response carries "List of encoded advertisements (up to `F_return` = 10)" and sets no message size limit. Every reply is read with `readLp(ServiceDiscoveryMaxMsgSize = 4096)`, while one advertisement may be up to `MaxXPRSize = 1024` bytes and the response is capped by count only. A registrar holding ten valid multi-address ads builds a response over 4096 bytes; the discoverer's read fails and it receives none of them.

The test does not assert the follow-on effect read from the code: the failed read is counted as a dial failure against the registrar, and five such failures remove it from the service tables. REGISTER exchanges stay under the limit and are not affected.

- Locations: `libp2p/protocols/service_discovery/types.nim:24` (the limit), `libp2p/protocols/service_discovery/connection.nim:78` (the reply read).
- Repro: `make test …_3` (expect: nonzero) → observed: exit 2, `Check failed: response.encode().len <= ServiceDiscoveryMaxMsgSize` and `Check failed: found.get().len == fReturn`; 3 tests run, 1 OK, 2 FAILED.
- Second pass: confirmed — read `connection.nim:78-82`, `types.nim:24` and `210-216`, `registrar.nim:433-441` and `lpstream.nim:227-240`, ran the test and saw the end-to-end lookup return fewer than `F_return` ads.
- Fix: make the limit and the response agree. Either derive the read limit from `fReturn * MaxXPRSize` plus closer peers and framing, or have the registrar stop adding ads once the encoded response would exceed the limit. A size-related read failure should not count as a dial failure.

#### Finding 5 (F-7f680511) — REGISTER and GET_ADS are encoded and dispatched as RPC types 16 and 17, not 6 and 7 — **confirmed**, medium severity, medium confidence, raised by second pass, adjudicated by merge pass

The spec's `MessageType` enum sets `REGISTER = 6` and `GET_ADS = 7`. The shared Kademlia codec defines `register = 16` and `getAds = 17`, and the service discovery handler dispatches on those symbols. Requests built here carry a type a spec-following registrar does not know, and a spec-following request is not routed to REGISTER/GET_ADS handling here.

The numbers live in `kademlia/protobuf.nim`, outside the audited unit; the unit's handler is where they take effect. The first pass saw the same numbers and left the row untraced for that reason. The finding does not establish why 16 and 17 were chosen, or any fault between nim-libp2p nodes.

- Locations: `libp2p/protocols/kademlia/protobuf.nim:36-37` (the enum values, outside the unit), `libp2p/protocols/service_discovery.nim:143-166` (the dispatch).
- Repro: `make test …_5` (expect: nonzero) → observed: exit 2, `Check failed: Message(msgType: Opt.some(MessageType.register)).encode() == @[8'u8, 6]`, `Check failed: decoded.get().msgType == Opt.some(MessageType.register)`, and the same pair for `getAds` and 7; 3 tests run, 1 OK, 2 FAILED.
- Second pass: raised it; ran the test and saw both wire-byte comparisons fail.
- Merge-pass adjudication: confirmed. Read the enum, the handler and spec lines 414–418, then ran the repro and saw the four failed checks above. Severity lowered from the second pass's high to medium, to match findings 1 and 2, which have the same kind of effect.
- Fix: decide which side is authoritative. Either set `register = 6` and `getAds = 7` in `kademlia/protobuf.nim` (a wire change that needs a network-wide switch) or change the spec's enum and request tables.

#### Finding 6 (F-ffd2e25a) — Ad for a requested service is rejected when another service entry has over 33 data bytes — **unconfirmed**, medium severity, low confidence, raised by second pass, adjudicated by merge pass

A note in the spec says "Any other entries in `xpr.services` are opaque to registrars and discoverers". XPR validation applies a 33-byte data limit to every `ServiceInfo`, so a signed ad that lists the requested service and fits the 1024-byte record limit is refused when an unrelated entry carries 34 data bytes.

The behaviour is reproduced. That the spec forbids it is not established: the sentence is in a note, a length cap does not read the entry's meaning, and the ExtensiblePeerRecord specification that may define the limit was not staged. The first pass passed this row on the same grounds. The test exercises the registrar's validation, which is outside the unit; the discoverer path the second pass names was not exercised.

- Locations: `libp2p/extended_peer_record.nim:74-84` (`isValid` for `ServiceInfo` and for the signed record); `libp2p/protocols/service_discovery/registrar.nim:188-190` (the same loop, outside the unit).
- Repro: `make test …_6` (expect: nonzero) → observed: exit 2, `Check failed: isValidAdvertisement(RegisterMessage(advertisement: Opt.some(encoded)), serviceId).isOk()` at test line 35; the size, decode and binding checks before it pass; 2 tests run, 1 OK, 1 FAILED.
- Second pass: raised it; ran the test and saw the ad with the extra entry fail registration validation.
- Merge-pass adjudication: unclear. Reproduced the failing check and read both validation sites. The reading of "opaque" against an XPR format limit cannot be settled without the XPR specification.
- Fix: check the XPR specification first. If it caps every entry at 33 bytes, clarify the note and change no code. If not, apply the per-entry limit only to the entry matching the requested `service_id_hash`.

#### Finding 7 (F-e21720ea) — Client-mode node keeps configured services in the signed XPR it publishes under its peer ID — **unconfirmed**, medium severity, low confidence, raised by second pass, adjudicated by merge pass

The spec says "Client mode nodes: MUST be only Discoverer". A client constructed with services keeps them in `disco.services` although registration is refused, `record()` signs that list into the node's own XPR, and the XPR publisher (started unconditionally, on by default) puts that record into the DHT under the node's peer ID.

The behaviour is reproduced for the publication candidate only: the test node is never started and no publication is observed. That this is the Advertiser role is not established. The client sends no REGISTER and is never returned by GET_ADS; only a peer that fetches the client's own record by peer ID sees the services list, and the spec separately has every participant store signed peer records under peer IDs. The first pass passed this requirement, taking Advertiser to mean registering ads; the second pass takes it to mean any signed, published statement of service participation.

- Locations: `libp2p/protocols/service_discovery.nim:175-182` (start keeps the services and starts the publisher), `libp2p/protocols/service_discovery/types.nim:309-316` (`record()` signs `disco.services`); `advertiser.nim:430-447` (`xprsToPublish`, outside the unit).
- Repro: `make test …_7` (expect: nonzero) → observed: exit 2, `Check failed: not decoded.get().advertisesService(service.id.hashServiceId())` at test line 22; 2 tests run, 1 OK, 1 FAILED.
- Second pass: raised it; ran the test and saw the signed candidate advertise the client's configured service.
- Merge-pass adjudication: unclear. Reproduced the failing check and read the constructor, `start`, `record()` and the publisher. Which reading of the role applies is a question for the spec's authors.
- Fix: if a client must disclose no service participation, clear or reject `services` when `client` is true, or have `record()` pass an empty list when not `isServer`. Otherwise state in the spec that the Advertiser role means registering advertisements, and close the finding.

### undefined-behaviour (prose-only)

#### Finding 4 (F-444a4fdc) — Inbound handler closes, not resets, the stream on an undecodable or unknown-type message — **unconfirmed**, info severity, low confidence

Stream Management says "Reset stream on protocol errors or validation failures". When an inbound frame fails to decode, exceeds the read limit or carries an unknown type, the handler returns and its `defer` runs `stream.close()`, a graceful close. The spec's own Error Handling table says "Invalid message format | Close stream", so the document disagrees with itself and the code follows one of its two statements.

Prose-only: no test was written or run by any pass.

- Locations: `libp2p/protocols/service_discovery.nim:131-145` (the `defer` and the read and decode error returns), `164-166` (unknown type).
- Repro: none (manual; code inspection).
- Second pass: unclear — read `service_discovery.nim:130-166` and both spec statements; asks whether "Close stream" permits a graceful close on malformed input or requires a reset.
- Fix: settle in the spec whether a malformed frame ends the stream by reset or by close, make the handler's error returns match, and add a test that sends an undecodable frame and observes the chosen termination.
