### contradicts-spec (proven violations, first-pass runs only)

#### Finding 2 (F-1b5e0f51) — Occupancy score is fixed at 100 when c >= C, so a full cache waits less than at C-1 and evicts — **unconfirmed**, medium severity, high confidence

The spec defines `occupancy_score = 1 / (1 - c/C)^P_occ` and says "As `c → C`: Score → ∞ (prevents overflow)"; its error table says "Cache full (registrar) | Issue ticket with waiting time". `waitingTime()` instead substitutes the constant 100 once the cache holds C entries, so the wait at c = C is far smaller than at c = C-1. A retry whose ticket has accumulated that time is Confirmed, and `AdvertisementCache.put` evicts the oldest unexpired ad to make room.

What it does not establish: the tests seed the cache directly. At the default `P_occ = 10` the wait at C-1 is clamped to `uint32.high` seconds, so the full-cache branch is not reached through REGISTER alone. It is reachable when the occupancy exponent is configured low enough for the wait near capacity to be finite.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:103-110` (the `c >= advertCacheCap` → `100.0` branch), `libp2p/protocols/service_discovery/advertisement_cache.nim:123-124` (`evictOldest()` on a full cache).
- Repro: the command above with `<n>` = 2, expect nonzero → observed by the first pass: `w(c = C-1) = 7101w3d6h28m15s, w(c = C) = 2h30m`; `Check failed: wFull >= wAlmostFull`; `Check failed: reply.status == kadprotobuf.RegistrationStatus.Wait`; `Check failed: before.allIt(it in after)`; 2 FAILED.
- Second pass: no verdict recorded.
- Fix: drop the `c >= advertCacheCap` special case so the `max(1e-9, 1.0 - ratio)` floor applies (the result is already clamped), or return the clamped maximum wait at c >= C. Separately, do not evict an unexpired ad for a new entry in `put`; answer Wait with a ticket.

#### Finding 3 (F-d8e97335) — Lower-bound state stores the ticket's t_wait_for (capped at E), not the calculated waiting time — **unconfirmed**, medium severity, high confidence

The spec's invariant is "a newly issued waiting time at time `t_current` MUST NOT be smaller than a previously issued waiting time by more than the elapsed time", with the update rule `bound(service_id_hash) = w_service` where `w_service = max(w_base, remaining_service_bound)`. `registration()` calls `updateLowerBounds` with `tWait` only after subtracting the ticket's accumulated time and capping it at E, so the stored bound never exceeds E. A previously issued waiting time above E therefore bounds the next request for the same service or IP by at most E minus the elapsed time.

Ambiguity considered: "issued waiting time" could be read as the ticket's `t_wait_for`. The first pass rejects that reading because the spec's own update rule assigns `bound = w_service`, with no E cap and no subtraction of served time. The merge pass finds that reasoning sound on the quoted text, but this is the finding where a second reviewer's reading of the clause matters most, and none was recorded. `updateLowerBounds` itself is not at fault; the caller hands it the wrong quantity.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:389-391` (`min(advertExpiry, tWait)` then `updateLowerBounds(..., tWait, now)`), `registrar.nim:374-376` (`waitingTime` result reduced by `updateWaitAfterRetry` before use).
- Repro: the command above with `<n>` = 3, expect nonzero → observed by the first pass: `w issued = 22h13m20s, bound stored = 1m40s`; `Check failed: stored == wPrevious`; `w_new = 50s, w_previous - elapsed = 22h12m30s`; `Check failed: wNew >= wPrevious - elapsed`; 1 FAILED. The second request's time is passed through `waitingTime`'s `now` argument instead of sleeping.
- Second pass: no verdict recorded.
- Fix: pass the value returned by `waitingTime()` (before `updateWaitAfterRetry` and before the cap) to `updateLowerBounds`; use the reduced, capped value only for `ticket.t_wait_for`. Then revisit `pruneExpiredEntries` (`registrar.nim:33-47`), which drops bound state E after its timestamp and would discard bounds still outstanding.

#### Finding 1 (F-27daf164) — waitingTime rounds w to whole seconds, so E*G becomes 0 and a first REGISTER is admitted ticketless — **unconfirmed**, low severity, high confidence

The spec says "The safety parameter `G` ensures waiting times never reach zero even when: Service similarity is zero (new service). IP similarity is zero (completely distinct IP)", and that a REGISTER without a ticket is answered with a new signed ticket and status `Wait`. `waitingTime()` rounds the formula result to the nearest second. With the defaults (E = 900, G = 1e-7) a new service from a distinct IP on an empty cache yields 9e-5 s, which rounds to 0; `registration()` then sees `tWait <= ZeroDuration` and returns Confirmed with no ticket on the first request.

What it does not establish: the lost wait is under one second. The effect is the missing ticket round trip, not a bypass of a long delay; requests with non-zero service or IP similarity are unaffected. G's term only survives rounding once occupancy is above roughly 58%.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:119-123` (`w = round(w)`), `registrar.nim:378-387` (`tWait <= ZeroDuration` → accept, Confirmed).
- Repro: the command above with `<n>` = 1, expect nonzero → observed by the first pass: `Check failed: w > ZeroDuration`; `Check failed: reply.status == kadprotobuf.RegistrationStatus.Wait`; `Check failed: reply.ticket.isSome()`; `Check failed: disco.countAdsInCache(serviceId) == 0`; 2 FAILED.
- Second pass: no verdict recorded.
- Fix: replace `round(w)` with `ceil(w)` at `registrar.nim:121`, or keep sub-second precision and round up only when filling `ticket.t_wait_for`. The existing test at `tests/libp2p/service_discovery/test_registrar.nim:52` encodes the rounding and needs updating.

#### Finding 4 (F-c114aaff) — registration() returns an empty Message when the key is absent: no REJECTED, no stream close — **unconfirmed**, low severity, high confidence

The spec says "Registrars MUST validate: … 2. `key` = 32 bytes (valid SHA-256) … Respond with `register.status = REJECTED` if validation fails", and its error table says "Missing required fields | Close stream". When the key is absent, `registration()` returns a default `Message`. A key of the wrong length does get Rejected a few lines later; only the absent key falls through. The reply encodes to zero bytes with no `register` field and no status.

What it does not establish: the test asserts the REJECTED reading. That the stream stays open instead of closing was read by the first pass in `connection.nim` and `service_discovery.nim` (outside the unit), not executed. No registrar state changes on such a request. The same early return in `getAdvertisements` (`registrar.nim:422-424`) is not filed, because the spec permits an empty list for GET_ADS.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:290-292` (`inMsg.key.valueOr: … return`).
- Repro: the command above with `<n>` = 4, expect nonzero → observed by the first pass: `reply on the wire: 0 bytes`; `Check failed: onWire.msgType == Opt.some(kadprotobuf.MessageType.register)`; `Check failed: onWire.register.isSome()`; status `== Opt.some(Rejected)` check failed; 1 FAILED.
- Second pass: no verdict recorded.
- Fix: treat an absent key like a wrong-length key and return the REGISTER message with status Rejected (`registrar.nim:301-310`), or let the caller close the stream for a request with missing required fields.

#### Finding 5 (F-b157a1c2) — waitingTime silently caps the occupancy exponent at 10, ignoring a larger configured P_occ — **unconfirmed**, low severity, high confidence

The spec's formula, "MUST be calculated using: w(ad) = E × (1/(1 - c/C)^P_occ) × (…)", uses P_occ as configured, and says "The higher the value of `P_occ`, the faster the increase". `waitingTime()` uses `min(discoConfig.occupancyExp, 10.0)` as the exponent, and the config constructor accepts larger values without error or warning, so a registrar configured with P_occ above 10 gets exactly the waiting times of P_occ = 10.

What it does not establish: the default (P_occ = 10) is unaffected; this matters only for a non-default configuration. Whether an implementation-imposed upper limit is an acceptable reading of "Implementations SHOULD modify them as needed" is a judgement no second reviewer weighed in on; the defect as filed is that the limit is silent.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:109-110` (`let exp = min(discoConfig.occupancyExp, 10.0)`).
- Repro: the command above with `<n>` = 5, expect nonzero → observed by the first pass: `w(P_occ=10) = 2h33m36s, w(P_occ=20) = 2h33m36s`; `Check failed: w20 > w10`; 1 FAILED.
- Second pass: no verdict recorded.
- Fix: use `discoConfig.occupancyExp` directly (the result is already clamped to `uint32.high` seconds), or enforce the limit visibly in `ServiceDiscoveryConfig.new`.
