### contradicts-spec (proven violations)

#### Finding 1 (F-27daf164) — waitingTime rounds w to whole seconds, so E*G becomes 0 and a first REGISTER is admitted ticketless — **confirmed**, low severity, high confidence

The specification says "The safety parameter G ensures waiting times never reach zero" and, for a REGISTER without a ticket, "Create a new signed ticket based on t_wait, and return the signed ticket in a response with status Wait." `waitingTime()` rounds the formula result to the nearest second. With the defaults (E = 900, G = 1e-7), a new service from a distinct IP gives 9e-5 s, which rounds to 0, and `registration()` answers the very first request Confirmed with no ticket. After rounding, G contributes nothing until occupancy is above roughly 58%.

What it does not establish: a long wait being skipped. What is lost is one ticket round trip of under a second. The Appendix allows admission when `t_wait` is 0; that does not cover a value the formula makes positive and the code rounds away.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:119-123` (clamp and `round(w)`), `registrar.nim:378-387` (`tWait <= ZeroDuration` admits).
- Repro: `REPRO(1)` → observed: `Check failed: w > ZeroDuration`; `status = ok(Confirmed)`, `Check failed: reply.status == kadprotobuf.RegistrationStatus.Wait`, `Check failed: reply.ticket.isSome()`; `3 tests run: 1 OK, 2 FAILED`.
- Second pass: confirmed — re-ran the proof (all ten first-pass proofs in one build, compiler passed as `NIMC`), read lines 115-117, 121 and 378 independently.
- Fix: replace `round(w)` with `ceil(w)` at `registrar.nim:121`, or keep sub-second precision and round up only when filling `ticket.t_wait_for`. Update `test_registrar.nim:52`, which pins the rounding.

#### Finding 2 (F-1b5e0f51) — Occupancy score is fixed at 100 when c >= C, so a full cache waits less than at C-1 and evicts — **confirmed**, medium severity, high confidence

The specification: "occupancy_score = 1 / (1 - c/C)^P_occ ... As c -> C: Score -> infinity (prevents overflow)" and, in Error Handling, "Cache full (registrar) | Issue ticket with waiting time". `waitingTime()` uses the constant 100 once the cache holds C entries, so the wait at c = C is far below the wait at c = C-1. A retry whose ticket has accumulated that time is Confirmed, and `AdvertisementCache.put` evicts the oldest unexpired ad to make room.

What it does not establish: reachability at the defaults. With P_occ = 10 the wait at C-1 is clamped to `uint32.high` seconds, so REGISTER traffic alone does not fill the cache; the proof seeds the cache through the cache API. The full-cache branch is reached with a smaller configured exponent. The second pass considers medium the upper end of the severity range.

- Locations: `registrar.nim:103-110` (constant 100 at capacity), `advertisement_cache.nim:123-124` (`evictOldest` on a full cache).
- Repro: `REPRO(2)` → observed: `w(c = C-1) = 7101w3d6h28m15s, w(c = C) = 2h30m`, `Check failed: wFull >= wAlmostFull`; `status = ok(Confirmed), evicted = 1`, `Check failed: before.allIt(it in after)`; `1 OK, 2 FAILED`.
- Second pass: confirmed — re-ran both tests and read `registrar.nim:104-105` and `advertisement_cache.nim:123-124`.
- Fix: drop the `c >= advertCacheCap` special case and let the `max(1e-9, 1.0 - ratio)` floor apply, or return the clamped maximum wait at capacity. Separately, do not evict an unexpired ad in `put` for a new entry; answer Wait with a ticket.

#### Finding 3 (F-d8e97335) — Lower-bound state stores the ticket's t_wait_for (capped at E), not the calculated waiting time — **confirmed**, medium severity, medium confidence

The specification: "a newly issued waiting time at time t_current MUST NOT be smaller than a previously issued waiting time by more than the elapsed time", `w_new >= w_previous - (t_current - t_previous)`, with the update rule `bound(service_id_hash) = w_service`. `registration()` hands `updateLowerBounds` the wait after subtracting the ticket's accumulated time and capping it at E. The stored bound therefore never exceeds E, and a waiting time of many hours bounds the next request for the same service or IP by at most E minus elapsed.

Ambiguity, stated by both passes: "issued waiting time" could mean the ticket's `t_wait_for = min(E, t_remaining)`. Read that way the MUST invariant holds and only the SHOULD update rule is broken. The specification's own `bound = w_service` (no cap, no subtraction) and "the final waiting time issued in the ticket is ... w_final" favour the reading filed. Hence medium confidence.

- Locations: `registrar.nim:389-391` (cap at `advertExpiry`, then `updateLowerBounds`), `registrar.nim:374-376` (`waitingTime`, then `updateWaitAfterRetry`).
- Repro: `REPRO(3)` → observed: `w issued = 22h13m20s, bound stored = 1m40s`, `Check failed: stored == wPrevious`; `w_new = 50s, w_previous - elapsed = 22h12m30s`, `Check failed: wNew >= wPrevious - elapsed`; `1 OK, 1 FAILED`.
- Second pass: confirmed — re-ran the proof and read lines 376, 389, 391, 160 and 171; raised the reservation above.
- Fix: pass the value `waitingTime()` returned to `updateLowerBounds`; use the reduced, capped value only for `ticket.t_wait_for`. Then revisit `pruneExpiredEntries`, which drops a bound E after its timestamp and would discard bounds that are still outstanding.

#### Finding 4 (F-c114aaff) — registration() returns an empty Message when the key is absent: no REJECTED, no stream close — **confirmed**, low severity, high confidence

The specification: "Registrars MUST validate: ... key = 32 bytes (valid SHA-256) ... Respond with register.status = REJECTED if validation fails", and "Missing required fields | Close stream". For a REGISTER without a key, `registration()` returns a default `Message`; it encodes to zero bytes, is written as the reply, and the handler keeps reading. Neither outcome the specification names happens. A key of the wrong length is handled (Rejected).

What it does not establish: the open stream by execution. The test checks the reply `registration()` returns; that the stream stays open was read in `connection.nim` and `service_discovery.nim`, which are outside the unit. A conforming advertiser always sets the key, so this is a malformed-request path. The same early return in `getAdvertisements` is not filed: the specification allows an empty list there.

- Locations: `registrar.nim:290-292` (`inMsg.key.valueOr: ... return`).
- Repro: `REPRO(4)` → observed: `reply on the wire: 0 bytes`, `Check failed: onWire.register.isSome()`; `1 OK, 1 FAILED`.
- Second pass: confirmed — re-ran the proof and read lines 290-310 and the two out-of-unit callers.
- Fix: treat an absent key like a key of the wrong length and return status Rejected, or give `handleMessage` a way to close the stream.

#### Finding 5 (F-b157a1c2) — waitingTime silently caps the occupancy exponent at 10, ignoring a larger configured P_occ — **confirmed**, low severity, high confidence

The specification's formula "MUST be calculated using" `1/(1 - c/C)^P_occ`, and "The higher the value of P_occ, the faster the increase". `waitingTime()` uses `min(discoConfig.occupancyExp, 10.0)`. A registrar configured with P_occ above 10 gets the waiting times of P_occ = 10, and the config constructor neither rejects nor reports it.

What it does not establish: any effect at the default P_occ = 10, which is unaffected.

- Locations: `registrar.nim:109-110`.
- Repro: `REPRO(5)` → observed: `w(P_occ=10) = 2h33m36s, w(P_occ=20) = 2h33m36s`, `Check failed: w20 > w10`; `1 OK, 1 FAILED`.
- Second pass: confirmed — re-ran the proof and read line 109 and `ServiceDiscoveryConfig.new`.
- Fix: use `occupancyExp` directly (the product is already clamped), or enforce an upper limit in `ServiceDiscoveryConfig.new` where the operator sees it.

#### Finding 6 (F-ca79c05f) — updateLowerBounds writes the one final wait into the service bound and every IP bound alike — **confirmed**, low severity, medium confidence

The specification keeps a bound per key: "w_ip = max(w_base, remaining_ip_bound); if w_base > remaining_ip_bound: bound(IP) = w_ip". The code computes one value, the maximum over the service and all IPs, and writes it into the service bound and every IP bound. A bound held by a service is copied to any IP that asks for it, and from that IP to the next service it asks for.

What it does not establish: a weakening of admission control. The code errs toward longer waits and the MUST invariant is still met. The second pass adds that under a per-key reading of that invariant the code's value is the stricter one and the specification's written per-IP rule would itself break the invariant; the specification is not consistent with itself here. The rule is introduced with SHOULD. A fix should settle the reading first.

- Locations: `registrar.nim:159-172` (same value to service and each IP), `registrar.nim:391` (single value passed in).
- Repro: `REPRO(6)` → observed: `bound(IP) stored = 5m, w_ip per spec = 9s`, `Check failed: ipBound == 9.secs`; `wait for an unrelated service from that IP = 4m59s`; `1 OK, 1 FAILED`.
- Second pass: confirmed — re-ran the proof and read `registrar.nim:123-145`, 159-172 and 391; raised the caveat above.
- Fix: return `w_base` alongside `w_final` and update each key from its own values; use `w_final` only for the ticket.

#### Finding 7 (F-96a3d84a) — AdvertisementCache.put inserts every element of ips, so one entry can count the same IP twice — **confirmed**, low severity, medium confidence

The specification: "Track IP addresses as a multiset: each IP is counted once per ad_cache entry that uses it". `put()` inserts the IP list as given. When the registrar has no connection IP it takes the list from the peerstore or its own listen addresses through `getIPs`, which returns one element per multiaddress. An advertiser known by two addresses on one host is counted twice for one entry.

What it does not establish: an effect on a remote REGISTER with an observed address, which supplies exactly one IP. Removal uses the same stored list, so counts do not leak.

- Locations: `advertisement_cache.nim:129-131` and `118-120` (`insertIps(ips)`), `registrar.nim:86-90` (fallback list).
- Repro: `REPRO(7)` → observed: `entries = 1, IP count = 2`, `Check failed: disco.registrar.ads.ipTree.ipsLen == 1`; `1 OK, 1 FAILED`.
- Second pass: confirmed — re-ran the proof and read `registrar.nim:86-90`, `advertisement_cache.nim:131` and `getIPs`. It raised finding 11 from the same fallback.
- Fix: deduplicate the list once, in `advertiserIps` or in `put`, so insert and remove stay symmetric.

#### Finding 11 (F-33157b82) — advertiserIps scores the sender's self-announced peerstore addresses when no observed IP exists — **confirmed**, low severity, medium confidence, raised by second pass, adjudicated by merge pass

The specification: "getIP(advertiser.addrs) is a function to get the IP addresses from the multiaddresses of the advertiser's connection information" and "The IP being refered to here is NOT the ad's but the one from the advertiser connection information." When a REGISTER arrives on a stream with no observed address, `advertiserIps()` falls back to the peerstore address book of the sender, which holds the listen addresses the sender announced. The sender therefore chooses the IP that is scored, bounded and counted in the IP tree.

What it does not establish: the behaviour over a real relayed or Tor stream. The test calls `registration()` in-process with an empty connection IP list and a peerstore entry the test writes. That such streams carry no observed address was read (`rconn.nim` never assigns `observedAddr`; the muxers copy the connection's value; `tortransport.nim:293` sets none). The specification does not say what to score when there is no connection information, so the test's assertion of equal waits is one acceptable outcome, not the only one. TCP, QUIC and WebSocket streams are not affected.

- Locations: `registrar.nim:83-90` (fallback to `peerStore[AddressBook][advertiser]`), `registrar.nim:373-374` (list passed to `waitingTime`).
- Repro: `REPRO(11)` → observed: `announced 200.1.2.3 -> wait 9s; announced 10.0.0.77 -> wait 12m29s`, `test_20261123T021802_f38c5f_11.nim(77, 18): Check failed: waitFar == waitNear`; `1 OK, 1 FAILED`.
- Second pass: raised it; ran the proof in a build that also selected proofs 1 and 10.
- Merge-pass adjudication: confirmed, reproduced. Ran `make test test_20261123T021802_f38c5f_11.nim NIMC=/w/cache/nim-2.2.14/bin/nim` (proof 11 alone; same compile and runner as the repro, with the compiler passed as `NIMC` because the PATH form was not permitted in the merge session). Exit 2 with the output quoted above. Read `registrar.nim:77-90`, `connection.nim:15-21`, the proof file, and checked that `rconn.nim` has no `observedAddr` assignment. Not traced by me: how identify fills a remote peer's address book.
- Fix: keep the peerstore fallback only for local registration (advertiser is the node's own peer id). For a remote sender with no connection IP return an empty list, which `ipsMaxScore` already scores as 1.0. Update the repo test "advertiserIps falls back to peerstore when connectionIps empty".

### undefined-behaviour (behaviour the specification leaves open)

#### Finding 8 (F-bad12a3d) — getAdvertisements builds replies larger than the 4096-byte read limit of the protocol's own peers — **confirmed**, medium severity, medium confidence

The specification says to "Include up to F_return advertisements" and names no message or advertisement size. `getAdvertisements()` puts up to ten cached ads plus closer peers into one reply with no size check. The registrar admits ads of up to 1024 bytes, while every message of this protocol is read with a 4096-byte limit. Five large ads for one service give a reply the discoverer refuses to read; it gets no ads and records a dial failure against the registrar.

What it does not establish: a departure from specification text. This is two of the implementation's own limits contradicting each other. It needs ads near the size limit: the second pass estimates that ten ads of about 200 bytes plus ten closer peers stay under 4096, and the first pass estimates that ten of about 350 bytes exceed it; neither figure was measured. The ads were seeded into the cache rather than registered through admission. The read limit and failure accounting are in `connection.nim`, outside the unit.

- Locations: `registrar.nim:436-445` (reply built without a size bound).
- Repro: `REPRO(8)` → observed: `ads in reply = 5, encoded reply = 5111 bytes, limit = 4096`, `Check failed: size <= ServiceDiscoveryMaxMsgSize`; over a localhost stream, `GET_ADS failed: connection reading failed: Message length 5111 exceeds maximum 4096`; `1 OK, 2 FAILED`.
- Second pass: confirmed — re-ran both tests and read `registrar.nim:436-445` and line 182.
- Fix: add ads and closer peers only while the encoded reply fits `ServiceDiscoveryMaxMsgSize`, or derive the limits from each other.

#### Finding 10 (F-09b5ed4f) — Every Wait reply adds lower-bound entries for its service id and source IPs, admitted or not — **unconfirmed**, medium severity, medium confidence

`updateLowerBounds` runs for every REGISTER answered with Wait and creates bound and timestamp entries for the service id and each source IP. Nothing ties them to the ad cache or the IP tree; they stay for E seconds. The specification says "Service-level entries are bounded by the number of distinct service_id_hash values currently tracked in the registrar state" and speaks of bounds "For each IP in the IP tree".

Why no verdict was reached: the second pass re-ran the proof, which fails as described, and confirmed the code facts, but could not settle the requirement. The same section also says "After the ticket is issued, the registrar updates the service-level lower-bound state" and "When a service_id_hash first enters the registrar state ... bound = 0". An implementation following that text keeps state for a service or IP that has only been issued a ticket, and would fail this test too; ticket grinding on a first request cannot be prevented without such state. The test's assertions encode one of the two readings. What would resolve it: the specification defining "registrar state" and saying whether lower-bound entries may exist without an ad_cache entry, and with what cap.

What it does establish: the growth is real (four table entries per fresh service id and source IP, kept for E seconds, keys chosen by the requester) and worth a cap whichever reading wins. Its size was reasoned, not measured; no sustained flood was run.

- Locations: `registrar.nim:391` (`updateLowerBounds` on every Wait), `registrar.nim:159-172` (entries created).
- Repro: `REPRO(10)` → observed: `services in cache = 0, service bounds held = 50; IPs in tree = 0, IP bounds held = 50`, four `Check failed` lines on the table sizes; `1 OK, 1 FAILED`.
- Second pass: unclear — ran the proof and read `registrar.nim:33-47`, 59-65, 154-172 and 391; the specification text supports both readings.
- Fix: settle the specification first, then bound the tables: keep entries only for services and IPs with cache entries, or cap the tables and evict the smallest remaining bound. The proof test encodes the first option.

### spec-drift (documentation drift)

#### Finding 9 (F-38998cca) — registration() answers Rejected when a cached ad of the same signer has a higher seqNo — **confirmed**, low severity, medium confidence

The specification, step 5: "If an entry for this peer_id and service_id already exists, this replaces it", and REJECTED is for "Invalid signature, invalid ticket, or error". The registrar sections know no sequence number. `registration()` checks `hasNewer` before any ticket or waiting-time handling and returns Rejected if the cache holds an ad by the same signer for this service with a higher seqNo; `put()` also drops other advertisers' older entries for that signer.

What it does not establish: a coding error. Three repository tests pin the rule, which looks like deliberate replay protection for signed records. The finding is that the document and the code disagree; the document may be what needs updating.

- Locations: `registrar.nim:346-353` (`hasNewer` → Rejected), `advertisement_cache.nim:110-113` (stale ad skipped in `put`).
- Repro: `REPRO(9)` → observed: `status = ok(Rejected)`, `Check failed: reply.status != Opt.some(kadprotobuf.RegistrationStatus.Rejected)`; `1 OK, 1 FAILED`.
- Second pass: confirmed — re-ran the proof and read `registrar.nim:346-353` and `advertisement_cache.nim:81-99`, 110-113; agrees that spec-drift is the right class.
- Fix: decide which side moves. If the seqNo rule stays, add it to the specification with the response for a stale ad. If the specification stays, remove the `hasNewer` rejection and let `put()` replace the entry.
