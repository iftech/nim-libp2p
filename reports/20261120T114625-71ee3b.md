Ambiguities worth a reader's attention:

- Findings 1 and 2 share a mechanism (a sub-half-second waiting time rounds to zero, so `registration()` confirms at once) but name different root causes — the `round()` at `registrar.nim:112-113` and the constant `100.0` at `registrar.nim:95-97`. Fixing the rounding (finding 1) alone would make a full cache answer Wait with a 1 s ticket, yet leaves the full-cache score far below its value at c = C-1; finding 2 stands on its own for that reason.
- Finding 1 rests on the normative Safety Parameter sentence. The specification's example REGISTER pseudocode does permit Confirmed when `t_wait <= 0`; a reviewer who reads the pseudocode as governing could dispute it. An existing unit test (`test_registrar.nim:124`) pins the current behaviour.
- Finding 3: the specification's removal clause is a SHOULD ("Once an ad has expired, it SHOULD be removed"); the MUST is the IP-count decrement on expiry. The finding's weight is on serving and counting entries past admission + E, not on the sweep period as such.
- Finding 5's proof calls `acceptAdvertisement` directly for two senders instead of driving two network REGISTERs, because the second REGISTER would first have to sit out the waiting time the first entry creates. It shows the cache keying, not an end-to-end exploit.
- Finding 10 does not affect the default configuration (P_occ = 10).
- Outside the unit, and therefore not a finding of this audit: the trace records `register = 16` and `getAds = 17` in `libp2p/protocols/kademlia/protobuf.nim` where the specification assigns `REGISTER = 6` and `GET_ADS = 7`, and a ticket signing input that hashes the ad rather than signing it raw. Both are marked untraced; the first deserves an audit of the kademlia unit.

### contradicts-spec (proven violations; finding 4 possibly document drift)

#### Finding 1 (F-1f3d589a) — waitingTime rounds w to whole seconds, so G vanishes and a first REGISTER is admitted with no wait — **unconfirmed**, medium severity, high confidence

Spec, Safety Parameter: "The safety parameter G ensures waiting times never reach zero even when: Service similarity is zero (new service). IP similarity is zero (completely distinct IP)." Handling REGISTER step 2: with no ticket, "Create a new signed ticket based on t_wait, and return the signed ticket in a response with status Wait." `Registrar.waitingTime` computes `w = E * occupancy * (serviceSim + ipSim + G)` and then rounds to whole seconds; with G = 1e-7 and E = 900 the G term is 9e-5 s, so the wait is exactly 0 and `registration()` confirms a ticket-less first REGISTER. G has an effect only once occupancy exceeds roughly 5555 (c/C above ~0.58). Not established: any overflow of the cache through this path alone.

- Locations: `libp2p/protocols/service_discovery/registrar.nim:112-113` (clamp and `round(w)`), `registrar.nim:368-369` (`tWait <= ZeroDuration` → `acceptAdvertisement`).
- Repro: `REPRO(f01)`, expect nonzero → observed by the first pass: exit 2, `Check failed: w > ZeroDuration`; `Check failed: register.status.get() == RegistrationStatus.Wait`; `Check failed: register.ticket.isSome()`; `Check failed: disco.countAdsInCache(serviceId) == 0`.
- Second pass: no verdict recorded.
- Fix: replace `round(w)` with `ceil(w)` in `waitingTime` (or carry milliseconds until the admission decision) so any positive w yields at least a 1 s ticket; update `test_registrar.nim:124` and the component test expecting an immediate Confirm.

#### Finding 2 (F-1b5e0f51) — Occupancy score is fixed at 100 when c >= C, so a full cache admits at once and evicts a live ad — **unconfirmed**, medium severity, high confidence

Spec, Occupancy Score: "As c -> C: Score -> infinity (prevents overflow)". Error Handling: "Cache full (registrar) | Issue ticket with waiting time". Once the cache is full `waitingTime` substitutes the constant 100.0, far below the value at c = C-1 (4^10 for C = 4). For a new service from a distinct IP the wait is 900 × 100 × 1e-7 = 0.009 s, rounded to 0: the REGISTER is Confirmed and `AdvertisementCache.put` evicts the oldest unexpired ad. The waiting time is non-monotonic in occupancy. Reaching zero wait from the network needs a service with no cached ads and an IP scoring 0; other requests still get a wait only 100× the bracket.

- Locations: `registrar.nim:95-97` (`if c >= advertCacheCap: 100.0`), `libp2p/protocols/service_discovery/advertisement_cache.nim:123-124` (`evictOldest` on a full cache).
- Repro: `REPRO(f02)`, expect nonzero → observed by the first pass: exit 2, "waiting time at c = C-1: 1m34s, at c = C: (zero)"; `Check failed: wFull >= wNearlyFull`; `Check failed: register.status.get() == RegistrationStatus.Wait`; `Check failed: disco.registrar.ads.contains(sid, advertiser)` (a seeded, unexpired ad was evicted).
- Second pass: no verdict recorded.
- Fix: make the `c >= C` branch return the maximum wait (it is capped to E afterwards) so a full cache always answers Wait; `evictOldest` then stays only as a defensive path.

#### Finding 3 (F-d9d70892) — Expired ads are only dropped by a sweep every E, so GET_ADS serves them for up to 2E — **unconfirmed**, medium severity, high confidence

Spec, Registrars: each cache entry has an "expiry timestamp based on admission time plus configured expiry time, E. Once an ad has expired, it SHOULD be removed". IP Similarity Score: "An entry expires after time E: MUST decrement the count for that IP". The cache stores the admission time but nothing compares it with the clock on read; the only removal is `pruneExpiredAds`, run by a heartbeat whose period is `advertExpiry`. An ad stays served, and keeps inflating c, c(service) and the IP score, for up to E after it expired.

- Locations: `libp2p/protocols/service_discovery.nim:50-53` (heartbeat with period E), `registrar.nim:425-426` (GET_ADS reads the cache unfiltered), `advertisement_cache.nim:31-43` (no timestamp check).
- Repro: `REPRO(f03)`, expect nonzero → observed by the first pass: exit 2, for an ad admitted E + 60 s ago: `Check failed: reply.getAds.get().advertisements.len == 0`; `Check failed: disco.registrar.waitingTime(...) == fresh.waitingTime(...)`.
- Second pass: no verdict recorded.
- Fix: filter on read (skip entries with `now - timestamp > E` in `getServiceCachedAds`, and exclude them from `len`, `serviceCacheAdsLen` and the IP tree) or prune before each use; shortening the sweep period only narrows the window.

#### Finding 4 (F-f765f301) — XPR ads are signed under domain libp2p-peer-record with payload type 0x0301, not the spec's values — **unconfirmed**, medium severity, high confidence

Spec, Advertisement Signature Verification: `assert(envelope.domain == "libp2p-routing-state")`, `assert(envelope.payload_type == "/libp2p/extensible-peer-record/")`. `ExtendedPeerRecord.payloadDomain` returns "libp2p-peer-record" and `payloadType` returns `03 01`, the pair the plain PeerRecord uses. An ad signed as the specification says fails `Advertisement.decode` here, and one produced here fails the specification's check. Not established: which side is wrong (the code matches libp2p RFC 0003; the XPR companion spec was not staged), nor an end-to-end interop failure against another implementation.

- Locations: `libp2p/extended_peer_record.nim:62-66` (`payloadDomain`, `payloadType`).
- Repro: `REPRO(f04)`, expect nonzero → observed by the first pass: exit 2, `Check failed: ExtendedPeerRecord.payloadDomain() == "libp2p-routing-state"`; `Check failed: Advertisement.decode(envelope.encode().get()).isOk()`; `Check failed: ExtendedPeerRecord.payloadType() != PeerRecord.payloadType()`.
- Second pass: no verdict recorded.
- Fix: decide which side is authoritative. To follow the LIP, return "libp2p-routing-state" and a payload type distinct from PeerRecord's, and re-sign stored records; to keep the code, correct the two asserts in the LIP.

#### Finding 6 (F-ed6745c6) — lookup counts distinct signed records toward F_lookup, so one advertiser can fill the quota — **unconfirmed**, medium severity, high confidence

Spec, Looking up services: "the discoverer SHOULD keep track of unique foundPeers, terminating the procedure once F_lookup advertisers have been found". The discoverer accumulates a `HashSet[Advertisement]` hashed by envelope signature and stops when its size reaches `fLookup`. Two records of one peer with different seqNo count as two, so the lookup ends early with duplicates of one advertiser while others further along the walk are never queried.

- Locations: `libp2p/protocols/service_discovery/discoverer.nim:125-128` (`found.incl(ad)` to the limit), `libp2p/protocols/service_discovery/types.nim:195-196` (hash by signature), `discoverer.nim:275-276` (walk ends on `found.len >= fLookup`).
- Repro: `REPRO(f06)`, expect nonzero → observed by the first pass: exit 2, "ads returned: 2, unique advertisers: 1"; `Check failed: advertisers.len == 2`; `Check failed: adQ.data.peerId in advertisers`.
- Second pass: no verdict recorded.
- Fix: track found advertisers in a `Table[PeerId, Advertisement]` keeping the highest seqNo; compare its length with `fLookup` and return its values.

#### Finding 5 (F-8d385f47) — ad_cache is keyed by the sending peer, so one advertisement can hold several entries per service — **unconfirmed**, low severity, high confidence

Spec, Handling REGISTER step 5: "If an entry for this peer_id and service_id already exists, this replaces it." `AdvertisementCache.put` keys by (serviceId, advertiser) where advertiser is the peer on the connection, not the peer_id in the ad. The same signed ad arriving from two senders with an equal seqNo is stored twice; GET_ADS returns it twice and c, c(service) and the IP multiset count it twice. Keeping the sender for IP scoring is what the specification asks; the divergence is using it as the key. The proof calls `acceptAdvertisement` directly, not two network REGISTERs.

- Locations: `advertisement_cache.nim:115-121` (replace only when `advertiser in peers[]`), `registrar.nim:369` (stream peer passed as key).
- Repro: `REPRO(f05)`, expect nonzero → observed by the first pass: exit 2, `Check failed: disco.registrar.ads.serviceCacheAdsLen(serviceId) == 1`; `Check failed: disco.registrar.ads.len == 1`; `Check failed: reply.getAds.get().advertisements.len == 1`.
- Second pass: no verdict recorded.
- Fix: key the per-service table by `ad.data.peerId`, keeping the sender only for IP accounting.

#### Finding 9 (F-c114aaff) — REGISTER with no key is answered with an empty message instead of REJECTED or a closed stream — **unconfirmed**, low severity, high confidence

Spec, REGISTER Request Validation: "key = 32 bytes (valid SHA-256) ... Respond with register.status = REJECTED if validation fails"; Error Handling: "Missing required fields | Close stream". `registration()` returns a default-initialised Message when the key is absent: no type, no register field, no status; the handler writes it and keeps the stream open. A wrong-length key is rejected correctly. No state is changed by such a request.

- Locations: `registrar.nim:282-284` (early `return` on a missing key).
- Repro: `REPRO(f09)`, expect nonzero → observed by the first pass: exit 2, `Check failed: isRegisterReply`; `Check failed: isRejected`.
- Second pass: no verdict recorded.
- Fix: return the Rejected message built at `registrar.nim:293-302` for a missing key, or reset the stream.

#### Finding 10 (F-b157a1c2) — waitingTime silently caps the configured occupancy exponent P_occ at 10 — **unconfirmed**, low severity, high confidence

Spec, Formula: "w(ad) = E x (1/(1 - c/C)^P_occ) x (...)"; System Parameters: "Implementations SHOULD modify them as needed". `waitingTime` raises the base to `min(discoConfig.occupancyExp, 10.0)`, so an exponent configured above 10 behaves as 10 with no warning. Defaults are unaffected.

- Locations: `registrar.nim:101-102`.
- Repro: `REPRO(f10)`, expect nonzero → observed by the first pass: exit 2, "P_occ = 10: 5d8h, P_occ = 12: 5d8h"; `Check failed: w12.seconds == 1843200`.
- Second pass: no verdict recorded.
- Fix: use `occupancyExp` as configured; enforce any upper bound in `ServiceDiscoveryConfig.new` so a misconfiguration is visible.

### missing-requirement (missing capabilities)

#### Finding 7 (F-5ab53e01) — Advertiser keeps no record of a Rejected registrar and re-registers with it on the next maintenance — **unconfirmed**, low severity, high confidence

Spec, Distributing ads across registrars: on Rejected the advertiser "MUST remove the registrar from the ongoing registrations for that bucket and SHOULD NOT attempt further registrations with this registrar for this advertisement." The MUST is met (the task ends and the slot is freed). Nothing remembers the registrar, so `maintainRegistrations` may pick it again for the same advertisement bytes each round — with certainty when the bucket holds at most K_register peers. The cost is one doomed REGISTER per maintenance period, not a burst.

- Locations: `libp2p/protocols/service_discovery/advertiser.nim:370-372` (`of Rejected: ... return`), `advertiser.nim:209-220` (candidates built with no rejected set).
- Repro: `REPRO(f07)`, expect nonzero → observed by the first pass: exit 2, `Check failed: not toSeq(advertiserNode.advertiser.running).anyIt(it.registrar == registrarId and it.serviceId == serviceId)`.
- Second pass: no verdict recorded.
- Fix: record (serviceId, registrar, hash of rejected advert bytes) on Rejected, exclude those registrars from candidate selection, and clear the record when the advert bytes change.

### undefined-behaviour (implementation-chosen limits)

#### Finding 8 (F-3142c75d) — GET_ADS reply of F_return accepted ads can exceed the 4096-byte read limit and is dropped whole — **unconfirmed**, medium severity, high confidence

Spec, GET_ADS Response: "List of encoded advertisements (up to F_return = 10)"; no maximum message size is given. A registrar accepts ads up to `MaxXPRSize` = 1024 bytes and replies with up to ten plus closerPeers, unbounded; the discoverer reads with `readLp(4096)`. Ten ads of ~480 bytes give a 4866-byte reply that the discoverer fails to read: it gets none of the ads, resets the stream and records a dial failure against an honest registrar. Anything above roughly 380 bytes per ad overflows.

- Locations: `registrar.nim:425-434` (reply built without a size bound), `libp2p/protocols/service_discovery/connection.nim:78-82` (`readLp(ServiceDiscoveryMaxMsgSize)`, failure recorded), `types.nim:24` (limit 4096).
- Repro: `REPRO(f08)`, expect nonzero → observed by the first pass: exit 2, "ad size: 483 bytes (limit 1024), encoded GET_ADS reply: 4866 bytes, reader limit: 4096"; `Check failed: found.get(@[]).len == fReturn` (0 of 10 returned).
- Second pass: no verdict recorded.
- Fix: derive the read limit from `fReturn * MaxXPRSize` plus closerPeers, or stop adding ads once the encoded reply would pass the limit; document the bound in the LIP.
