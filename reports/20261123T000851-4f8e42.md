### contradicts-spec (proven violation: finding 1; demonstrated behaviour against a Note: finding 5)

#### Finding 1 (F-61f16619) — lookup counts advertisements, not unique advertisers, toward F_lookup — **confirmed**, medium severity, high confidence

The spec says "The discoverer MUST attempt to find up to `F_lookup` advertisers" and "SHOULD keep track of unique `foundPeers`, terminating the procedure once `F_lookup` advertisers have been found". The lookup instead collects a `HashSet[Advertisement]` hashed by envelope signature and stops when that set reaches F_lookup. Two adverts signed by one advertiser (an older copy and a re-signed one with a newer seqNo) count as two. The lookup ends with fewer than F_lookup unique advertisers, discards other advertisers it was offered, and returns the same peer twice. The DiscoveryTracker is not affected; it deduplicates by peer id but does not control the returned result or the stop condition.

- Locations: `libp2p/protocols/service_discovery/discoverer.nim:125-128` (limit applied to the advert count), `discoverer.nim:256` (found set typed by advert), `discoverer.nim:275` and `:188` (stop conditions), `types.nim:185` (hash by signature, outside the unit).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T000851_4f8e42_1` → observed by the scan: `test_20261123T000851_4f8e42_1.nim(83, 22): Check failed: advertisers.len == fLookup` and `(84, 16): Check failed: found.len == advertisers.len`.
- Second pass: confirmed — read `discoverer.nim:113-128`, `256-294` and the hash in `types.nim`, and ran the test independently; both checks failed.
- Fix: key the found set by advertiser peer id (keep the advert with the highest seqNo), apply F_lookup to the number of distinct peer ids, and return one advert per peer.

#### Finding 5 (F-bb8151eb) — Discoverer drops signed ads when an unrelated service's data exceeds 33 bytes — **confirmed**, low severity, medium confidence, raised by second pass, adjudicated by merge pass

The spec's signature verification section says "Any other entries in `xpr.services` are opaque to registrars and discoverers - they are meaningful only to the application that ultimately receives the advertisement." After verifying the signature and the requested service, `validAds` calls `isValid`, which applies the 33-byte `ServiceInfo.data` limit to every service in the signed record. A valid advert within the overall record size limit is dropped from lookup results and from the tracker when a different service carries more than 33 bytes.

What this does not establish: the quoted sentence is in a Note and has no MUST, and the staged spec defines no `ServiceInfo.data` limit either way. The 33-byte limit is a deliberate local policy that this implementation's own record builder enforces, so adverts built by this implementation never trigger the drop; the effect is on adverts from other implementations or applications. No security effect is shown.

- Locations: `libp2p/protocols/service_discovery/discoverer.nim:44-46` (the `isValid` call), `libp2p/extended_peer_record.nim:74-84` (the per-entry check, outside the unit), `extended_peer_record.nim:18` (`MaxServiceDataSize = 33`).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T000851_4f8e42_5` → observed: `test_20261123T000851_4f8e42_5.nim(76, 9): Check failed: ad in found`, `[FAILED ] lookup accepts a signed ad with unrelated service metadata`.
- Second pass: raised it, with the proof test.
- Merge-pass adjudication: confirmed. I ran the test on the proof branch with Nim 2.2.14: it exits nonzero on the `ad in found` check, while the `control in found` check on the line before passes, so the reply was delivered and only the advert with the unrelated oversized entry is missing. The test's preconditions (record within `MaxXPRSize`, decodes with a valid signature, advertises the requested service) are `require`d and held. I read the code path and checked the quoted sentence against the staged spec.
- Fix: in `validAds`, apply the data-size policy only to the entry for the requested service and leave unrelated entries for the application; or have the spec state a per-entry limit normatively.

### missing-requirement (proven violations)

#### Finding 2 (F-15dfc6ac) — GET_ADS query that times out is cancelled with no retry and no backoff recorded — **confirmed**, medium severity, high confidence

The spec's Error Handling table says "Timeout | Close stream, retry with exponential backoff". When a registrar does not answer GET_ADS within the lookup timeout, `collectBucketAds` breaks out and cancels the query. The stream is reset, but the timeout is not recorded as a failure: nothing is retried and no backoff applies. A registrar that accepts the stream and stays silent is never backed off or evicted, so every later lookup can pick it again and wait the full timeout for its bucket.

What this does not establish: the test expresses "retry with exponential backoff" through the implementation's existing backoff book (`dialFailures` / `dialBackedOff`). A fix that retried inside the lookup with its own schedule would satisfy the spec without satisfying the assertion as written. Dial errors, stream errors and undecodable replies are already backed off.

- Locations: `libp2p/protocols/service_discovery/discoverer.nim:173-175` (break on deadline), `discoverer.nim:157-165` (pending queries only counted and cancelled), `connection.nim:37-93` (cancellation bypasses `recordDialFailure`; outside the unit).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T000851_4f8e42_2` → observed by the scan: `(73, 16): Check failed: registrar in disco.dialFailures` and `(74, 25): Check failed: disco.dialBackedOff(registrar, addrs)`; the request-sent, cancelled and stream-reset checks pass.
- Second pass: confirmed — read `discoverer.nim:153-175`, `273-290` and `connection.nim:37-93`, and ran the test independently; both checks failed.
- Fix: call `recordDialFailure(peerId, addrs)` for every query still pending at the deadline, so the existing exponential backoff and eviction apply.

#### Finding 3 (F-38a27514) — dispatchGetAds accepts a response whose type is missing or not GET_ADS — **confirmed**, low severity, high confidence

The GET_ADS response table says "`type` | REQUIRED | `GET_ADS` (7)" and Error Handling says "Missing required fields | Close stream". `dispatchGetAds` only checks that the reply carries a `getAds` field and never reads the message type, so a response typed REGISTER, or with no type, is processed as a valid GET_ADS response and its advertisements and closer peers are accepted.

What this does not establish: advertisements are still signature-checked, so this is a conformance gap and not a trust bypass. The spec has no explicit discoverer-side "MUST validate type" sentence; the reading combines the field table with the Error Handling row. The numeric value of the GET_ADS enum is defined outside the unit and was not assessed.

- Locations: `libp2p/protocols/service_discovery/discoverer.nim:87-88`.
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T000851_4f8e42_3` → observed by the scan: the GET_ADS control passes; `(71, 79): Check failed: (await lookupWithReply(Opt.some(kad_protobuf.MessageType.register))) == 0` and `(74, 70): Check failed: (await lookupWithReply(Opt.none(kad_protobuf.MessageType))) == 0`.
- Second pass: confirmed — read `discoverer.nim:76-98`, `connection.nim:91-95` and `kademlia/protobuf.nim:92-99`, and ran the test independently; the control passed and both rejection checks failed.
- Fix: return an error in `dispatchGetAds` unless `reply.msgType == Opt.some(MessageType.getAds)`.

### undefined-behaviour (demonstrated behaviour, clause interpretation open)

#### Finding 4 (F-ddddd736) — Discoverer accepts more than F_return advertisements from a single registrar — **unconfirmed**, low severity, medium confidence

The response table says "List of encoded advertisements (up to `F_return` = 10)" and System Parameters defines F_return as the "max number of service-specific peers returned from a single registrar". The discoverer never applies F_return to a response: every advert that validates is accepted, limited only by the message size cap and F_lookup, so one registrar can supply most of a lookup's results. The only text that tells the discoverer to cap is the non-normative appendix ("If it returns more we can just randomly keep `F_return` of them").

What this does not establish: a breach of a MUST. Both passes agree on the behaviour; neither found normative text that says whether an over-limit response is invalid or whether the limit binds only the sender. Honest registrars of this implementation cap at F_return.

- Locations: `libp2p/protocols/service_discovery/discoverer.nim:95` (whole list passed on), `discoverer.nim:30-49` (no count limit in `validAds`).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T000851_4f8e42_4` → observed by the scan: `(80, 16): Check failed: found.len <= fReturn` with F_return = 3 and 12 adverts from one registrar.
- Second pass: unclear — reproduced the over-limit acceptance, but found the normative text does not settle whether the receiver must cap. A normative receiver rule in the spec would resolve it.
- Fix: keep at most `discoConfig.fReturn` adverts per response in `dispatchGetAds`, or have the spec state the discoverer-side rule normatively.
