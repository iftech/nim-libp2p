### contradicts-spec (proven violations)

#### Finding 1 (F-e89a894e) — maintainRegistrations re-selects a registrar that replied Rejected and re-sends the same advert — **confirmed**, low severity, high confidence

The spec says: "If the status is Rejected, the advertiser MUST remove the registrar from the ongoing registrations for that bucket and SHOULD NOT attempt further registrations with this registrar for this advertisement." The MUST half holds. The SHOULD NOT half does not: `advertiseToRegistrar` just returns on Rejected and nothing records the rejection, so the next `maintainRegistrations` pass finds the bucket below K_register, treats the rejected registrar as an ordinary candidate and starts a new task with the same advertisement bytes and no ticket. A Rejected reply also clears the dial-failure record, so the dial backoff does not hold the registrar back.

This does not establish more than a wasted REGISTER exchange per rejecting registrar per maintenance interval (default 10 min) per service. In a bucket with more than K_register peers the re-selection is a random draw, not a certainty.

- Locations: `libp2p/protocols/service_discovery/advertiser.nim:370-372` (Rejected branch returns, no state kept), `advertiser.nim:209-220` (candidates exclude only registrars with a running task).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T021808_90fc52_1; rc=$?; git ls-files --error-unmatch tests/.gitignore >/dev/null 2>&1 || rm -f tests/.gitignore; exit $rc` → observed: `test_20261123T021808_90fc52_1.nim(114, 52): Check failed: rejecting.dialed.countIt(it == registrar) == 1`.
- Second pass: confirmed — ran the proof (exit 2, same check failed, the three `require` guards before it passed) and re-derived the mechanism in the code. It agrees with severity low.
- Fix: keep, per provided service, the set of registrars that rejected the current advertisement; add to it in the Rejected branch; exclude it when building `candidates`; clear it when the advertisement bytes change or the service is removed.

#### Finding 2 (F-467e83c0) — maintainRegistrations drops a Confirmed registration whose registrar left the bucket and refills it — **confirmed**, low severity, medium confidence

The spec defines `K_register` as "Max number of active (i.e. unexpired) registrations + ongoing registration attempts per bucket", and says a Confirmed registration is kept in the registrar's `ad_cache` for E seconds, after which the advertiser removes it from the ongoing registrations. `maintainRegistrations` cancels any task whose registrar is no longer in the bucket's peer list, including one sleeping out E after Confirmed, stops counting it and starts a registration with another peer of the same bucket. Nothing withdraws the first advert, so the bucket holds K_register + 1 unexpired registrations until the first one expires.

Ambiguity, which is why confidence is medium: the spec does not say what an advertiser does when a registrar with a live registration drops out of AdvT. The finding rests on reading the K_register definition and the E lifetime together. Where the registrar was evicted as unreachable, early replacement is defensible; the over-count matters when the registrar is alive and was merely replaced in a full bucket. The test drives the table directly with `removePeer`/`insert` and the registrar is a stub, so the still-cached advert is argued from `registrar.nim`, not observed. The excess is bounded by the number of evicted registrations and by the remainder of E.

- Locations: `libp2p/protocols/service_discovery/advertiser.nim:191-202` (stale sweep does not tell an attempt from a Confirmed registration), `advertiser.nim:204-220` (slot refilled).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T021808_90fc52_2; rc=$?; git ls-files --error-unmatch tests/.gitignore >/dev/null 2>&1 || rm -f tests/.gitignore; exit $rc` → observed: `test_20261123T021808_90fc52_2.nim(132, 46): Check failed: confirming.dialed.deduplicate().len <= KRegister`.
- Second pass: confirmed — ran the proof (same check failed, `require` guards passed) and re-derived the mechanism. It agrees with the caveats above and adds that the stale sweep is skipped for a bucket that became empty (`advertiser.nim:186-187`), so the cancel happens only when the bucket has another peer to refill from.
- Fix: mark a task as confirmed (for example a `confirmedAt` field set in the Confirmed branch) and cancel a stale task only while it is still attempting; keep counting a Confirmed one toward its bucket until E ends. If early replacement of unreachable registrars is intended, document it as a deliberate divergence from K_register.

#### Finding 3 (F-2023a4e3) — A Wait ticket whose zero t_wait_for is absent on the wire ends the task with no retry scheduled — **confirmed**, medium severity, medium confidence, raised by second pass, adjudicated by merge pass

The spec says: "If the status is Wait, the advertiser MUST schedule a next registration attempt to the same registrar based on the ticket.t_wait_for value included in the response", and that the ticket MUST be included in that attempt. `advertiseToRegistrar` reads `t_wait_for` as an optional field. When it is absent from the wire it logs "Ticket without a wait time" and returns: no retry is scheduled and the ticket, held only in the task, is lost. The same reply with an explicit 0 is retried after the 1 s floor, so only the encoding differs.

Why absence can mean zero: the second pass reports that the spec declares `uint32 t_wait_for = 4` without an `optional` label, so an encoder with implicit field presence leaves a zero value off the wire, and that sub-second waits (which round to 0 whole seconds) are the ordinary first reply of a lightly loaded registrar under the spec's waiting-time formula. The repository itself reads an absent `t_wait_for` as zero when building the ticket signing input (`kademlia/protobuf.nim:186`).

What this does not establish: that any deployed registrar sends such bytes. The spec's schema says proto2 yet writes unlabelled scalars, so presence is left to the encoder. This repository's own registrar always writes the field (`registrar.nim:397`), so nim-to-nim is unaffected. The omitting registrar in the proof is a stub.

- Locations: `libp2p/protocols/service_discovery/advertiser.nim:362-364` (return on absent `tWaitFor`); related, outside the unit, `libp2p/protocols/kademlia/protobuf.nim:75` (field declared `Opt[Duration]`).
- Repro: `export PATH=/w/cache/nim-2.2.14/bin:$PATH; make test test_20261123T021808_90fc52_3; rc=$?; git ls-files --error-unmatch tests/.gitignore >/dev/null 2>&1 || rm -f tests/.gitignore; exit $rc` → observed: control test `[OK]`, then `test_20261123T021808_90fc52_3.nim(130, 12): Check failed: dials >= 2` and `(131, 6): Check failed: running`.
- Second pass: raised it, with the proof and a run showing the failure above.
- Merge-pass adjudication: confirmed. I ran the proof on head `b41ad20b` (exit 2; control passed in 1.01 s, proof test failed on both checks; 3 tests run, 2 OK, 1 FAILED). I read the proof file: the two tests differ only in `tWaitFor` being `Opt.some(ZeroDuration)` or `Opt.none`, so the failure isolates the absent field. I read `advertiser.nim:20-27` and `355-369`, `protobuf.nim:75` and `186`, and `registrar.nim:372-398`, and they are as the second pass described. I could not read the staged spec text, so the Ticket definition and the registrar step 6 wording are taken from the second pass; the Wait sentence matches the trace's requirement text. Confidence stays medium for that reason and because no foreign registrar was exercised.
- Fix: in the Wait branch treat an absent `t_wait_for` as zero (`newTicket.tWaitFor.get(ZeroDuration)`) and continue to `ticketWait`, which already floors the delay. End the task only when the Wait reply carries no ticket at all.
